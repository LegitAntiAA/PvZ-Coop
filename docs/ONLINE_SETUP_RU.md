# Общий онлайн-сервис: инструкция владельцу мода

Этот документ предназначен владельцу общего сервиса и разработчику сборки.
Один Cloudflare Worker обслуживает браузер комнат всех игроков. Его адрес и
публичный STUN встроены в клиент; игроки получают готовый архив, открывают
браузер комнат и создают комнату либо присоединяются к ней.

Worker хранит список комнат и передаёт SDP/ICE. Игровые данные идут напрямую
между игроками через надёжный упорядоченный WebRTC DataChannel, зашифрованный
DTLS. TURN не используется.

Общий сервис опубликован по адресу
[pvz-coop-signaling.rostov20172017.workers.dev](https://pvz-coop-signaling.rostov20172017.workers.dev/health).
11 ноября 2026 года его `/health` вернул HTTP 200,
`{"service":"pvz-coop-signaling","schema":1}`. Ниже сохранены шаги для
повторного развёртывания и обслуживания этого сервиса.

Cloudflare разрешает SQLite Durable Objects на Workers Free. Бесплатный тариф
имеет квоты; при их превышении операции останавливаются до сброса лимита.
Для этого проекта выбирайте Free, без подключения платного тарифа.
Актуальные условия: [официальная тарификация Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/).

## 1. Подготовить единый дистрибутив

Раздавайте обычным игрокам одинаковый готовый архив мода, содержащий
`PlantsVsZombies.exe`, `datachannel.dll`, необходимые ресурсы и уведомления о
лицензиях. Весь Cloudflare-вход, публикацию и привязку сервиса к сборке выполняет
владелец мода. Учётная запись Cloudflare и настройка адресов игрокам не нужны.

Для сборки разработчиком нужны Git, CMake и Visual Studio C++ Build Tools.
После развёртывания сервиса и включения его адреса в исходники (разделы 2–3)
выполните в PowerShell из корня репозитория:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\BuildOnlineDeps.ps1 -Platform Win32
```

Скрипт получает точные ревизии libdatachannel 0.24.5, Mbed TLS 3.6.7 и их
зависимостей в `work/vendor`, собирает DLL и кладёт её в `lib/online/Win32`.
При уже существующей изменённой ревизии скрипт завершается с объяснением,
сохраняя локальные файлы. Он не меняет системные пути DLL или настройки защиты.

Затем соберите `PlantsVsZombies.sln`, `ReleaseGOTY`, `Win32`. Рядом с итоговым EXE
должна находиться DLL той же архитектуры. Для x64 сначала запустите скрипт
с `-Platform x64` и соберите игру для x64. LAN и одиночная игра могут работать
без необязательной DLL; онлайн-браузер при её отсутствии объяснит, чего не хватает.

Одна сборка получает собственный идентификатор. Раздавайте всем игрокам один
и тот же готовый архив: даже одинаковый исходный код, собранный повторно, может
получить другой номер. В браузере видны только комнаты точно такой же сборки;
прямое подключение с другим идентификатором также отклоняется.

## 2. Развернуть единый бесплатный Cloudflare Worker

Эту настройку один раз выполняет владелец общего сервиса. Полученный URL
используется при сборке клиента для всех игроков.

1. Откройте [Cloudflare Dashboard](https://dash.cloudflare.com/) и войдите или
   создайте аккаунт. В разделе Workers & Pages выберите бесплатный Workers Free.
   Собственный домен не требуется: подходит адрес `workers.dev`.
2. Установите Node.js, совместимый с закреплённым Wrangler. Проверенный локально
   комплект использует Node.js 24.16.0 и Wrangler 4.160.1.
3. Откройте PowerShell в `online/signaling` внутри репозитория и выполните:

   ```powershell
   npm.cmd ci
   npx.cmd wrangler login
   ```

4. Wrangler откроет браузер для входа. Пройдите вход самостоятельно и разрешите
   доступ к нужному Cloudflare аккаунту. API-токен не нужно вставлять в чат,
   игру, `coop.ini` или репозиторий.
5. Проверьте `wrangler.jsonc`. Поле `name` задаёт имя Worker. Можно оставить
   `pvz-coop-signaling` или выбрать свободное имя. Не удаляйте привязку
   `DIRECTORY`, класс `RoomDirectory` и миграцию `new_sqlite_classes`: именно
   SQLite-вариант подходит для Free.
6. Опубликуйте Worker:

   ```powershell
   npm.cmd run deploy
   ```

7. Скопируйте HTTPS-адрес, выведенный Wrangler, например
   `https://pvz-coop-signaling.your-subdomain.workers.dev`.
8. Откройте этот адрес с `/health` в конце. Ожидается JSON с
   `service: "pvz-coop-signaling"` и `schema: 1`.

Публикацию и вход выполняет владелец аккаунта. Адрес опубликованного общего
сервиса предоставил владелец; для проверки `/health` доступ к его аккаунту
или учётным данным не потребовался.
Дополнительная документация: [команды Wrangler](https://developers.cloudflare.com/workers/wrangler/commands/),
[WebSocket Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

## 3. Привязать общий сервис к выпускаемой сборке

Передайте разработчику конечный HTTPS-адрес Worker после успешного `/health`.
Разработчик задаёт `NET_ONLINE_SERVICE_ENDPOINT` в
`Lawn/Net/NetServiceConfig.h` и собирает дистрибутив из раздела 1. Для текущей
сборки закреплён `https://pvz-coop-signaling.rostov20172017.workers.dev`.
Это единственное место привязки общего адреса. Публикуйте один и тот же архив
для всех участников.

Клиент автоматически соединяется с общим сервисом при открытии браузера комнат.
В игровом интерфейсе нет полей URL и STUN; эти параметры не настраиваются через
`coop.ini`. Публичный STUN `stun:stun.cloudflare.com:3478` задан константой
`NET_ONLINE_STUN_SERVER` в том же файле. Адрес приведён в
[официальной документации Cloudflare](https://developers.cloudflare.com/realtime/sfu/get-started/connection-patterns/).

`/signal` добавляется автоматически к корневому адресу Worker. Если общий URL
изменится, обновите сервисную константу, пересоберите мод и раздайте новый
единый архив. Изменение логики Worker по прежнему адресу обычно требует только
`npm.cmd ci` и `npm.cmd run deploy` из той же папки и аккаунта.

Обычный путь игрока: открыть браузер комнат, выбрать существующую комнату или
создать свою с названием, необязательным паролем и лимитом 2–4 участника,
включая хоста. Для защищённой комнаты клиент вводит её пароль. Комнаты с активной
игрой показывают это состояние; позднее подключение обрабатывает игровой клиент.

Пароль не передаётся в URL и не отображается в списке комнат. Клиент вычисляет
PBKDF2-SHA256 с уникальной случайной солью и 100 000 итераций. Worker хранит
проверочное значение в состоянии комнаты, сравнивает его без раннего выхода
по совпадающему префиксу и ограничивает повторные неверные попытки в сессии.

Игровые снапшоты через Worker не проходят.

## 4. Ограничения прямого подключения

STUN помогает узнать внешний адрес, но не пересылает игровой трафик.
Некоторые сочетания симметричного NAT, CGNAT и ограничительных сетевых экранов
не позволяют установить прямое соединение. Без TURN гарантировать подключение
между любыми двумя сетями нельзя. При неудаче клиент завершает попытку и
показывает причину; автоматического платного реле нет.

Для таких сетей остаются другая сеть или уже поддерживаемый LAN/VPN-путь.
Официальное описание ограничений STUN и роли TURN:
[WebRTC: TURN server](https://webrtc.org/getting-started/turn-server).

## 5. Локальная проверка разработчиком

Локальный Worker не требует входа в Cloudflare и публикации:

```powershell
cd online\signaling
npm.cmd ci
npm.cmd test
npm.cmd run dev
```

В отдельном PowerShell из корня репозитория:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\BuildOnlineDeps.ps1 -BuildTests
.\work\online-native\build-Win32\Release\NetOnlineTests.exe http://127.0.0.1:8787
```

Нативный тест создаёт четыре клиента без окон. Он проверяет версии, пароль,
полноту комнаты, состояние игры, кик, завершение потоков и реальный обмен через
ICE/DTLS/SCTP: максимальный кадр 65 538 байт и 32 упорядоченных сообщения.
Он также проверяет состояние подключения каталога до регистрации, после
ошибки и после остановки, а также сохранение соединения во время восьмисекундного
ожидания, отказ до открытия DataChannel и повторный вход после него.
Успешный результат — `ONLINE_TESTS passed=22 failed=0`; тест Worker — 9/9.
Это проверка транспорта на одном компьютере. Для проверки NAT нужен отдельный
запуск с участниками из двух разных внешних сетей.

Полный двухпроцессный сценарий игры через тот же Worker запускается отдельно:

```powershell
.\tests\CoopSmoke\RunCoopSmoke.ps1 -Background -Scenario Adventure1 -SkipIntro 0 -OnlineEndpoint http://127.0.0.1:8787
```

Он создаёт отдельную защищённую комнату для своего run ID, использует штатный
игровой протокол и проверяет совпадение применённых снапшотов. Runner требует
следов реального принятого DataChannel на обеих сторонах и отклоняет TCP-путь.
`-OnlineEndpoint` — закрытый параметр разработческого smoke-runner; он не
создаёт настройку URL у игрока. Для проверки опубликованного Worker замените
локальный адрес в этой тестовой команде на его HTTPS URL.

## Частые ошибки

| Сообщение | Что проверить |
| --- | --- |
| `WebRTC runtime missing` | `datachannel.dll` рядом с EXE, правильная Win32/x64 архитектура, установлен подходящий Microsoft VC++ Runtime. |
| `Signaling connection failed` | Оператор проверяет `/health`, публикацию, действительный TLS-сертификат и встроенный в сборку адрес. |
| `version-mismatch` | Все участники запустили EXE из одного готового архива. |
| `wrong-password` | Пароль комнаты; после ошибки выдержите предложенную задержку. |
| `room-full` | Лимит включает хоста и клиентов, ещё устанавливающих ICE-соединение. |
| Пустой список | Участники используют одинаковый архив; хост оставил игру запущенной; обновите список. Оператор проверяет общий сервис. |
| `Direct connection failed` | Возможны ограничения NAT/сети; используйте другую сеть либо LAN/VPN. |
